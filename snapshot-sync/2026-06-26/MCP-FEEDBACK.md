# MCP Feedback — 2026-06-26 snapshot sync

## Stale client-side tool cache made `get_snapshot_diff`'s newest pair appear unavailable — 2026-08-27 (snapshot-sync-plan)

**Operation**: Checking whether `get_snapshot_diff` had a `2026-05-11/2026-06-26` pair to diff against, needed for this sync's Changed-detection (the raw TSV baseline for 2026-05-11 has no content columns to compare against — see below).
**What MCP provided**: Calling `get_snapshot_diff` with no arguments returned the `2025-04-24/2026-05-11` pair's data, and the tool's own description text (fetched via `ToolSearch`) still listed only that one pair as "Available snapshot pairs."
**Gap**: The `2026-05-11/2026-06-26` pair was actually live on the server the whole time (deployed in commit `a6639eb`, confirmed by another session) — this session's connection was serving a stale, client-cached copy of the tool's description/behavior from before that deploy. Explicitly passing `snapshotPair: "2026-05-11/2026-06-26"` on a live call (rather than relying on the no-args default or the cached description text) worked correctly and returned real data immediately.
**Workaround**: Explicitly specify `snapshotPair` on every `get_snapshot_diff` call rather than trusting the no-args/default behavior or a previously-fetched tool description to reflect the latest deployed pair. No MCP-side data loss occurred — this was purely a client-cache staleness issue, most likely resolved by reconnecting the MCP session, but explicit `snapshotPair` is a cheap, robust habit regardless.
**Enterprise Impact**: A CI-driven sync pipeline that calls `get_snapshot_diff` without a `snapshotPair` argument (relying on "give me the latest pair") would have silently kept diffing against a now-superseded pair, or found no pair at all, after a fresh server deployment — exactly the trap this session almost fell into, requiring nearly a full plan-authoring pass to be redone once the real pair was confirmed live.
**Suggested Enhancement**: A lightweight way to programmatically list currently-available `snapshotPair` values (the tool's own docstring says "Call with no argument to see available pairs" but the actual behavior is to run the default pair's diff, not list options) would let a calling session self-detect staleness instead of trusting a cached description.
**Commented-out candidate**: None identified.

## `get_spec_snapshot('types')` footer reports zero items despite real content — 2026-08-27 (snapshot-sync-plan)

**Operation**: Downloading the `types` artifactType (SIMPLETYPE/AMOUNT/EXTSCHEMA/USERDEF records) as part of assembling a complete `spec-snapshot.tsv`.
**What MCP provided**: The response's `# Section: types | Page 1 of 1 | Total items in section: 0` footer line claims zero items, but the actual body contains 366 real, well-formed data rows (339 SIMPLETYPE + 17 AMOUNT + 8 EXTSCHEMA + 2 USERDEF — matching `get_repository_statistics`' separately-reported totals exactly).
**Gap**: The footer's item count for this one artifactType doesn't reflect the actual row count returned — every other artifactType's footer (messages, components, choices, codesets, business) matched its real row count exactly.
**Workaround**: Counted actual `grep -c` rows per record type instead of trusting the footer, and cross-checked against `get_repository_statistics`' independently-reported Simple Types/External Schemas/User-Defined Entries totals (they matched exactly), confirming the data itself is complete and correct — only the footer's count is wrong.
**Enterprise Impact**: An automated pipeline that gates "did I get a complete download" on the footer's stated count (a reasonable, exactly-what-the-tool-tells-you-to-do check per this project's own "COMPLETENESS IS MANDATORY" convention) would falsely conclude the `types` section failed and either retry needlessly or abort the sync entirely, even though the actual data was fine.
**Suggested Enhancement**: Fix the `types` artifactType's footer item-count calculation to match its actual row count, consistent with every other artifactType.
**Commented-out candidate**: None identified.

## Comparing against the 2026-05-11 baseline TSV required abandoning content-diffing entirely — 2026-08-27 (snapshot-sync-plan)

**Operation**: Diffing the new `2026-06-26` snapshot against the library's actual synced baseline (`snapshot-sync/2026-05-11/spec-snapshot.tsv`) to find Changed items — not an MCP call issue per se, but a data-shape mismatch between two `get_spec_snapshot` outputs captured at different times.
**What MCP provided**: The 2026-05-11-era download has `MSGDEF` rows with only 5 fields (`type/name/isoId/businessArea/status`) and `MSGCOMP`/`CHOICE`/`CODESET` rows with only 4 (`type/name/isoId/status`) — no checksum, no definition text at all, predating both the 2026-08-26 checksum deployment and (apparently) an even earlier deployment that added bulk definition text.
**Gap**: A naive content comparison (e.g. treating the last field as "definition") against this baseline is actively wrong, not just incomplete — the last field in an old row is `status`, so comparing it against a real definition string in the new row makes ~100% of everything look "changed." This was caught before it reached a plan (a first draft using this approach reported CHOICE/CODESET both 100% "changed," an obvious red flag), and fully resolved once `get_snapshot_diff`'s real pair was confirmed live (see entry above) — but a session without that fallback would have had no reliable way to detect field-level content changes for this specific transition at all.
**Workaround**: Used `get_snapshot_diff`'s `changedContent` section (once its stale-cache issue was resolved) as the authoritative source for Changed detection instead of any TSV-vs-TSV comparison.
**Enterprise Impact**: Any pipeline whose "detect changes" step is "diff two `get_spec_snapshot` TSV captures" rather than "call `get_snapshot_diff` between two named snapshot dates" is silently exposed to this exact failure mode whenever the bulk TSV's own column schema evolves between the two capture dates — which will keep happening as the server adds fields (as it just did twice in two days this session).
**Suggested Enhancement**: None specific to the tool itself — this is more a documentation note for future snapshot-sync-plan runs: prefer `get_snapshot_diff` over TSV-vs-TSV comparison whenever a live snapshot pair is available; only fall back to raw TSV comparison when no pair exists, and even then, key by isoId presence/absence only (never by row-content comparison across TSVs whose schema versions might differ).
**Commented-out candidate**: None identified.
